# Flight Sim: memory

## Project in one paragraph
Flight Sim is a browser 3D flight simulator: Three.js 0.186 + Vite 8, plain JavaScript ES modules, static hosting on GitHub Pages, no backend, no external assets (every model, texture, sound and map is generated by code at run time). 14 aircraft (light prop, turboprops, jet trainer, business jets, airliners, fighters), 3 generated maps of 60 km (grasslands, desert, snow) with 11-13 airports each, weather and day/night, ATC with AI airport traffic, systems and failures, an autopilot, time compression, a chart with waypoints, a crash sequence, game modes (Quick Flight, Free Flight, Career, Emergency, VIP Escort) with an economy, three save slots, full keyboard/mouse/controller operation, synthesized audio and accessibility options. Live build: https://coder-4847.github.io/Flightsim/

## How a new session should start
1. Read this file. `git status`, `git log --oneline | head`, then `npm ci` if node_modules is missing.
2. Dev server: `nohup npx vite --port 5199 --host 127.0.0.1 &` (it dies whenever the sandbox resets; restart it before any browser test). `/models.html` is the model viewer.
3. Headless checks (fast, run before every push): `node scripts/modetest.mjs` (must print "all passed"), `node scripts/simtest.mjs`, `node scripts/aptest.mjs` (also `TUNED=1`), `node scripts/apils.mjs`, `node scripts/tuningtest.mjs`, `npx vite build`. After any model change also `node scripts/seethrough.mjs <aircraftId|all>` (needs the dev server from step 2).
4. Browser checks use Playwright with the system Chromium and software GL (`--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`; about 1-5 fps, so drive the simulation directly through `window.__flightsim` rather than relying on frame timing, and expect HUD updates at about 1 Hz). Handy calls: `__flightsim.startFlight({aircraftId, mapId, airportCode, startMode: 'runway'|'air'|..., hour, mode: 'quick'})`, `__flightsim.session.model.crashWith('x')`, `session.controls.autopilot / time / waypoints`. Environment facts for this sandbox: Playwright is not in the repo's dependencies, it is preinstalled at `/opt/node-tools/node_modules/playwright/index.mjs` (import it by that path) and the Chromium binary is `/opt/pw-browsers/chromium` (pass it as `executablePath`, never run `playwright install`); Python has PIL and numpy for image diffs; `pkill -f vite` can kill your own shell (exit code 144) so stop the dev server by pid or just let it die. The throw-away Playwright scripts (start a flight, wait for `state.current === 'flying'`, screenshot) lived in the session scratchpad, not in the repo; only `scripts/seethrough.mjs` was kept. Recipes: see the fence test in "Fence, approach guide and fighter see-through round".
5. Model work: take 4-6 screenshots per aircraft from `/models.html?id=<id>&yaw=..&pitch=..&d=..` (yaw 0 looks at the tail, 90 from the right, 180 from the nose; `d` about 1.5 x the aircraft length fills a 800x500 frame), list defects, fix, re-render, run `scripts/seethrough.mjs`, then check the in-game chase view.
6. Agent lessons: parallel worktree agents hit the user's shared usage limit repeatedly, and a finished agent can keep sending duplicate completion notices (stop it with TaskStop). Prefer focused direct work; use agents only for genuinely separable big jobs.

## Touch controls (added after rc.3)
- Request: "controls for mobile ... control yoke, a rudder slider ... all the buttons we have on pc" so phones and iPads can play.
- Design: the on-screen controls feed the same action layer as the keyboard. `Input.virtualDown(action, down)` (held actions), `Input.virtualTap(action)` (press + release) and `Input.touch = {yoke, rudder, pitch, roll, yaw}` (analog; applied in `FlightControls.update` like a gamepad stick, with the `touchCurve` expo and optional `touchInvertPitch`). `FlightControls.setThrottle(v)` is used by the throttle slider (switches autothrottle off). The autopilot disconnects when the yoke is pushed past 0.3.
- Code: `src/ui/touchControls.js` (everything; created in `flightHud.js`), CSS block "Touch controls" at the end of `src/style.css` (sizes in `vmin` via `--u`, safe-area insets, `touch-action: none`), settings in `settings.js` (`touch*` keys, shown in the Controls tab), camera orbit/pinch in `main.js` (own pointer deltas, not movementX), chart pinch and +/-/Centre in `mapScreen.js`.
- Behaviour: `body.touch-ui` is set when touch is on; it hides the dashboard, toolbar, flight hint and cam info and moves the data strip to the top. Portrait shows a "Rotate your device" overlay. HUD panels are pinned to the middle strip in touch mode (not draggable) so they never cover the controls. MENU sheet closes after one-shot actions and stays open for repeatable ones (time, throttle presets, engine select).
- Tested with Playwright mobile emulation (844x390 phone and 1180x820 iPad, CDP touch events, software GL): yoke, rudder with simultaneous yoke, throttle, flaps, lights, brakes hold, MENU sheet, autopilot panel, chart open/pinch/tap-waypoint/close, one-finger orbit, pinch zoom, console clean. NOT tested on a real phone or iPad (no device here): real thumb comfort, iOS Safari quirks (address bar, no fullscreen API on iPhone, audio unlock) and sizing on very small screens are unverified. Bug found by the emulation: the MAP touch button sits under the chart's Close button, so the browser's follow-up click closed the chart at once; the chart now ignores clicks for 600 ms after opening (compare `e.timeStamp`, not `now()`, because slow frames delay handling). Touch UI size is `--u = min(1vmin, 0.46vw)` so the bottom row fits 4:3 iPads. Tip for players: on iOS use Share > Add to Home Screen for a fullscreen, bar-less view.

### 1. Breakable fences
- **Files**: `src/world/airport/fence.js` (new: `FenceField`, `Debris`, `aircraftHull`), `src/world/airport/props.js` (`addFence` now only computes the perimeter and returns `{ box, total, edges, height: 2.4 }`; it no longer writes quads and posts into the merged buffers; the perimeter road is unchanged), `src/world/airportBuilder.js` (builds `new FenceField(fenceSpec, mats, detailGroup)` after the materials exist, stores it in `group.userData.fence`, adds it to `disposables`; `AirportManager.update(camPos, wind, dt = 0)` steps the debris; new `AirportManager.collide(model, dt)`), `src/scene/flightScene.js` (passes `dt` to `airports.update`; this `dt` is already multiplied by the time-compression scale), `src/game/session.js` (`update(dt)` calls `flightScene.airports?.collide(this.model, dt)` right after `model.step(dt)`), `src/flight/flightModel.js` (new `applyImpulse(r, J)`).
- **Fence geometry**: every airport class except `strip` has a rectangular fence (hub box u -2150..2150, v -560..560; regional u +-1500, v +-650; airfield u +-720, v -90/-230..230/90 depending on the side), 2.4 m high. It is built from the four edges as chain-link *bays* about 4 m wide (a bay is one stretched `PlaneGeometry`, DoubleSide fence material from `buildingMaterials`, alpha-tested texture `fenceTexture()`, 4 m x 2.4 m cell) and a steel *post* (0.12 m square, 2.9 m tall) at every bay boundary. Both are `InstancedMesh`es (so a hub has about 2,700 bays and 2,700 posts but only two draw calls), placed in the airport frame (`frame` group: local +X along the main runway, +Z to its right, local y = 0 is the airport elevation). The geometries carry an all-white `color` attribute because the airport materials use `vertexColors: true` (without it an instanced mesh renders black). They live in the airport's detail LOD group, so they exist visually only within about 5.2 km of the airport centre. `ctx.gate` (a gap in the fence at the landside gate) is read but nothing sets it, so there is no gate gap in practice (same as before).
- **Collision** (`FenceField.collide`, called through `AirportManager.collide`): early outs are a crashed aircraft, more than 40 m above the airport, more than 2.7 km from it, and not within `hull.radius + 4` m of any fence line (`near()`). The aircraft hull (`aircraftHull(spec)`, cached on the model as `model.fenceHull`) is a list of points with radii: the three wheels (radius = `wheelRadius + 0.15`, ignored while `gear.extension <= 0.5`), every `spec.strike` point (0.45), a line of points every 2 m between the outermost left and right strike points (the wing, 0.5) and a line every 2 m from the rearmost to the foremost gear/strike x at the mean height of the centre-line strike points (the fuselage, 0.9). Each point is rotated by the aircraft attitude, its velocity is `v + w x r` (body rates `w` rotated into world axes), and both are converted into the airport frame (`lx = dx cos t - dz sin t`, `lz = dx sin t + dz cos t`, `t = frame.rotation.y`). `FenceField.hit` then tests the point against each fence edge: it must be within `radius + 0.2 + |v_perp| x dt` of the line (the swept term stops fast aircraft tunnelling through at 120 Hz), below `2.4 + radius` and above `-radius/2`, and moving faster than 0.5 m/s horizontally (so parked or pushed-back aircraft never eat the fence). Every bay whose span overlaps the point's extent along the fence is torn off; posts within `radius + 0.4` along the fence are snapped when the point speed is over 9 m/s or the post is already bent, otherwise bent over (a lean of 0.5-0.7 rad away from the aircraft, applied to that instance's matrix).
- **Debris** (`Debris`): a torn bay becomes a loose centred plane mesh (`bayLooseGeo`, scaled to the bay width) and a snapped post a loose box, both parented to the fence root, so they follow the airport frame. Rigid-body physics in the airport frame with gravity 9.81, linear drag `exp(-0.35 dt)`, angular drag `exp(-0.6 dt)`, inertia of a box, 8 contact points for a panel (corners, edge mid-points) and 3 for a post (ends and middle) against the flat ground at y = 0. Contact: position push-out, impulse along +y with restitution 0.25 (0 below 2 m/s impact speed) and Coulomb friction 0.55 along the surface, two passes per step; a piece sleeps after touching with |v|^2 < 0.04 and |w|^2 < 0.12 for 0.5 s. Substeps: up to 4 steps of about 1/90 s per frame. At most 400 pieces per airport (oldest removed first). Launch velocity: 55-85 % of the hitting point's velocity plus a +-1.5 m/s horizontal scatter and 1-3.5 m/s upward, with random spin scaled by speed. Masses: 16 kg per 4 m bay, 14 kg per post. Scatter is deterministic (`hash(seed)`), not `Math.random`. Debris is only stepped while the airport's detail LOD is visible and is not saved; it disappears when the airport streams out and is rebuilt intact when it streams back in.
- **Cost to the aircraft**: the momentum given to the debris (`sum m x v`) comes back as `-p` at the contact point through `FlightModel.applyImpulse(r, J)`: `vel += J / mass`, and the angular part `(r x J)` rotated to body axes divided by the scaled inertia (`inertia.{roll,yaw,pitch} x mass / mass.ref`). Off-centre hits therefore yaw or roll the aircraft a little. It never touches `damage`, never calls the crash code, and `applyImpulse` ignores a crashed aircraft. The existing ground-strike and hard-landing rules are unchanged.
- **Tested** (headless Chromium with software GL, driving `__flightsim.session.update(1/120)` directly): start any flight, take the first built airport (`session.flightScene.airports.built`), find `group.userData.fence.edges[1]` (the +u end of the box, 80 m away from the aircraft), `model.reset({mode: 'runway', x, z, heading})` 80 m before it, release the parking brake, set `model.vel` along the heading, step 8 s of simulation and call `flightScene.airports.update(camera.position, {x:0,z:0}, 1/120)` each step; for screenshots set `session.cameras.towerPosition`, `cameras.setMode('tower')` and `session.paused = true`. ### 3. Fighter see-through
- **Why the earlier sweeps missed it**: looking for magenta behind the model only finds missing geometry. A face that is present but wound the wrong way is culled when seen from outside, so you look through it at the inside of the part (dark ellipse, hollow tube) and the silhouette still looks closed.
- **The check** (`scripts/seethrough.mjs`, kept in the repo): `node scripts/seethrough.mjs <aircraftId|all> [distance] [outDir]` with the dev server on port 5199 (override `PORT`, `PLAYWRIGHT_MODULE`, `CHROMIUM`). For ten views per aircraft it screenshots `models.html?id=..&bg=ff00ff&air=1&lod=2&d=..`, then sets every material to `DoubleSide`, screenshots again and compares in a canvas: background -> covered = `holes` (see-through), covered in both but very different colour = `inside-out`. It prints both counts per view and writes an overlay PNG (yellow holes, red inside-out) to `/tmp/seethrough` by default. Expect small non-zero counts from glass, propeller discs, open nozzle liners and intake ducts, which are open or double-sided on purpose; look for views with hundreds of hole pixels or a large jump. Validated on the Warden: before the fixes the rear view showed 943 hole pixels and the underside views 811 and 512, after the fixes 32, 66 and 42, and the inside-out counts fell two to four times. A second, more local check was used during the work but not kept: render each mesh alone with FrontSide and DoubleSide from 14 directions with an orthographic camera and list meshes whose silhouette differs (it located the aileron and missile meshes).
- **Bugs found and fixed**:
  1. `aircraft/models/kit.js loftBody` end caps (`capStart`/`capEnd`, added on 2026-10-15) were wound backwards on both ends (`if (nx < 0) ci.push(0, a, b); else ci.push(0, b, a);` is the corrected order). Effect: the closed rears of the Corsair and Warden were still see-through from behind in game, and the F-16 and trainer caps were reversed too.
  2. `kit.js prepStations` (used by `loftBody`) now sorts the stations by ascending x. The Warden's tail booms and stinger were written with descending x, so the interpolation evaluated the wrong interval and the lofts came out inside-out (booms invisible from outside, a dark ellipse where the inside showed). After the sort the Warden has proper twin booms carrying the fins; its silhouette changed a little (for the better). All other `loftBody` callers already used ascending x, so nothing else changes.
  3. `kit.js wingSurface`: the "upper surface must face +Y" decision used a noisy sum over vertices and was wrong for thin aft slices, so the Corsair and Warden ailerons (and similar trailing-edge pieces) were inside-out. It now tests one upper-skin triangle in the middle of the span (index 75 % along the first run). Also added: the flat cut face at the hinge line (the second run of a panel with `xf1 < 1`) is oriented aft separately from the skin. This second change did not alter the check numbers; it is a safeguard.
  4. `aircraft/models/jetkit.js missileParts`: the body and seeker profiles ran from nose to tail (descending x) and the wingtip missiles were hollow from outside. The profile order is reversed (ascending x).
  5. `kit.js revolve` (a `LatheGeometry` about the X axis, used for spinners, probes, missiles, nozzle liners): it only faces outward for ascending-x profiles; descending ones were inside-out. Found on the side because the check flagged the Skyhawk's nose: **every propeller spinner (Skyhawk, Caravan, King Air, ATR) was hollow from the front**, and the pitot probes were inside-out too. `revolve` now flips winding and normals when the first profile point has a larger x than the last, so both orders come out outward (verified with a 24-triangle test and the viewer: the Skyhawk spinner is now a solid, correctly lit cone). Side effect to be aware of: the small `steel` flame-holder ring inside the fighter nozzles (profile descending) now faces outward instead of inward; it looked fine in the viewer rear views but was not examined closely. Equal-x profiles (flat discs, the wheel hub) are left as they were.
- **Remaining, judged minor** (not fixed): a few pixels of gap along the lower rim of the nozzle outer shell (hornet rear view about 270 px); the missile tail end and seeker cone are open shells; gear doors and wheel discs are single-sided thin panels; the nozzle liner and intake ducts are open on purpose; propeller discs are transparent on purpose. The all-aircraft sweep before and after the fixes also lists, unchanged, thin slivers under the airliner wing roots and fairings (Citation 554 px at yaw 300 / pitch -30, bizjet 315, jumbo 509, widebody 382), the Citation rear view (146), and a patch of about 40 x 12 px (at d = 12) on the Skyhawk's cabin roof where the wing root meets the fuselage (visible in the yaw 45 / pitch 10 and yaw 225 / pitch 25 overlays; a real hole, not fixed, start here if the user reports the Skyhawk) and the same patch on the Caravan (353 px). They were not investigated; if the user reports see-through airliner or Skyhawk parts, start from `node scripts/seethrough.mjs <id>` and the overlay PNGs.
- **Not verified**: on a real GPU, or in the in-game chase view after the final fixes (checked in the model viewer with software rendering only; the chase distance for the F-16 is about 32 m, inside the HIGH LOD range of 8 x length).

## Aircraft upgrades (2026-10-16)
User's request (paraphrased): "Add an upgrade system for each jet. Give each of the 14 planes their own stats and purchasable upgrades with Cr, like top speed, ascent rate, stuff like that. Not too cheap, not too expensive, progressively more expensive. Each upgrade can be upgraded about 5 times, every upgrade costs more than the last, so there is something to do after buying all the jets. Update memory.md, push so I can playtest."

Design (all in `src/progress/tuning.js`, pure data and arithmetic, no DOM):
- **Six tracks x five levels per aircraft** (`TRACKS`, `MAX_LEVEL = 5`, `MAX_UPGRADES = 30`). The levels are per aircraft (`save.tuning = { aircraftId: { engine: 2, drag: 1, ... } }`), so upgrading the Skyhawk does nothing for the Zenith. Each track edits a private copy of the spec (`specWithTuning(spec, levels)`; the stock spec object is never modified; copies are cached by `id:livery:levels`; no tuning returns the very same spec object):
  1. **Engine tuning** `engine`: +5% per level (max +25%) to `power` and `staticThrust` (piston, turboprop) or `thrust` and `thrustDry` (turbofan); `fuelFlowMax`/`fuelFlowAb` +2% per level. Faster acceleration, shorter take-off, better climb, higher top speed.
  2. **Streamlining** `drag`: `aero.cd0` and `gearCd` -4% per level (max -20%), `limits.vne` +1.5% per level, `mmo` +0.01 per level. Higher top speed and better economy.
  3. **Lightweight airframe** `weight`: `mass.empty` -2% per level (max -10%). Better climb and acceleration, shorter take-off, lower stall speed.
  4. **Control surfaces** `handling`: `clDa`, `cmDe`, `clDr`, `cnDr` +5% per level, `controls.rate` +4%, and for the FBW fighters `fcs.rollRate` +6%. Sharper roll, pitch and rudder.
  5. **Gear and brakes** `gear`: `gear.brakeMu` +6% per level, `limits.hardLanding` and `crashLanding` +4% per level (max +20%: a harder touchdown before gear damage or a crash; the grade bands Smooth/Good/Firm are fixed in fpm, only the Hard/Very hard split moves, so the fare bonus is not exploitable).
  6. **Fuel efficiency** `fuel`: `fuelFlowIdle/Max/Ab` -5% per level (max -25%, so +33% range).
  The shop shows each track's real before and after number for that aircraft (`track.stat(spec)`: "Thrust 129 kN -> 135 kN", "Vne 750 kt -> 761 kt", "Empty weight 8,570 kg -> 8,399 kg", "Roll rate 320 -> 339 deg/s" for the FBW fighters and "Control response +5%" for the others, "Hard-landing limit 750 -> 780 ft/min", "Range about 1,430 km -> 1,510 km" (rough still-air estimate from capacity, 60% of max flow and cruise speed)).
- **Prices** (`referenceFare`, `upgradePrice`, `remainingCost`): the yardstick is the reference fare of that aircraft, a 15 km hop at 75% load with the landing fee (Skyhawk 3,006 cr, Trekker 3,594, Tutor 4,000, Regal 4,500, Cirrus 72 6,001, Zenith CJ 5,500, Stratos 6,794, Regional 175 7,499, Meridian 9,000, Atlas 10,999, Titan 13,001, Falcon 5,000, Corsair 6,500, Warden 8,000). The Nth purchase on an aircraft (counting all six tracks together, so every purchase is dearer than the last whichever track it goes into) costs `reference fare x 1.2 x 1.1^N`, rounded to 50 cr, minimum 500. Skyhawk: first 3,600 cr, 10th 8,500, last (30th) 57,200, everything 593,300 cr. Titan: first 15,600, last 247,500, everything 2.57 M. All 14 aircraft together 18.4 M cr (the 14 aircraft themselves total 4.66 M). So an upgrade costs one to two flights early on and 10 to 20 flights at the end. `SaveManager.buyTuning(aircraftId, trackId)` works the price out itself (the caller does not pass it), needs the aircraft owned, refuses a maxed track, charges, persists (`autosave`) and returns `{ ok, price, level }`.
- **Wiring**: `saves.tuningFor(id)`, `tuningBought(id)`, `nextTuningPrice(id)`; `sanitizeSave` clamps levels, drops unknown tracks, unknown aircraft and aircraft the pilot does not own (so old saves and imports are fine); the modes pass `tuning: saves.tuningFor(aircraftId)` in `startOptions()` (`freeflight.js`, `contract.js` for Career and VIP, `emergency.js`), and `FlightSession.start` builds `specWithTuning(specWithLivery(...), opts.tuning)`. Quick Flight passes nothing, so it is always the stock aircraft. Career, VIP and Emergency loan aircraft the pilot may not own; they use whatever tuning the save has for that aircraft id (usually none).
- **UI**: `src/ui/shopScreen.js` has a new tab **Upgrades** (id `tuning`; the old pilot-wide tab, id `upgrades`, is now labelled **Pilot perks**: approach assist, terrain awareness, cabin pack, cargo pack, hull insurance, unchanged). Left: the pilot's aircraft with `n/30`; right: the model preview, six rows (name, five pips, level, blurb, "now -> next" numbers, Buy button with the price, "Maxed") and a line with the next price and the cost of everything left. The notice line says what was fitted. CSS `.tune-row`, `.pips` at the end of `src/style.css`. The hangar spec sheet (Free Flight) uses the tuned spec and shows "Upgrades: n of 30 fitted". The About screen and README mention the system.
- **Autopilot**: a more powerful aircraft hunted more with the autothrottle and a more responsive one with the stick, so `Autopilot.profile` now has `thrustK` and `controlK` (1 / `spec.tuneRatio.thrust` and `.control`; the tuned spec carries `tuneRatio` = {thrust, control} set by the engine and handling tracks) that scale the autothrottle rate and the stick outputs back. `TUNED=1 node scripts/aptest.mjs` (and `apils.mjs`) runs the same checks on every aircraft fully upgraded, `ONLY_TRACK=<id>` limits it to one track, `TRACE=1` prints the altitude trace.
- **Measured effect of all 30 upgrades** (`node scripts/tuningtest.mjs`, software physics only, sea-level take-off, level flight at 3,000 ft held with a little stick; handling excluded from the top-speed run): take-off roll -25% to -31%; climb rate 25 s after lift-off +27% to +95% (Skyhawk 711 -> 1,201 ft/min, jumbo 2,513 -> 4,074, F-16 17,807 -> 22,629; the turboprop airliner gains most); level top speed +5% (jumbo; near its Mach limit) to +28% (Corsair), Skyhawk 116 -> 139 kt; roll rate +12% to +36% (Skyhawk 98 -> 116 deg/s, F-16 270 -> 361); 50 kt braking distance -17% to -20%. No crashes anywhere. These are big at the end on purpose (it is the long-term goal) but the airliners probably feel better than they need to; if it feels too strong cut `per` in the engine and weight tracks first.
- **Tests**: `scripts/modetest.mjs` section "aircraft upgrades (tuning)": price monotonic for every aircraft, first upgrade 1-2 reference fares, last more than 10x the first, every track applies on every aircraft, stock spec untouched, caches, stat text, buying flow (unowned aircraft, unknown track, cannot afford, rising price across tracks, per-aircraft separation, all 30 bought with ever-rising prices, maxed refused, persistence), `sanitizeSave` of the tuning table, and a flight check (a maxed Skyhawk takes off at least 15% shorter and climbs 30% better). Browser check (Playwright, dev server): created a pilot with 60,000 cr, Fly > Shop > Upgrades, bought Engine tuning and Streamlining (4,350 + 3,950 cr as shown: first 3,600, second 3,950), screenshot looks right, then launched a Free Flight in the Skyhawk and `session.model.spec.tuning` was `{engine: 1, drag: 1}` with power 140,700 W (= 134,000 x 1.05); console clean.
- **Known limits / open**: (1) fully upgraded Tutor T-39 hunts in the autopilot altitude-capture scripts (2 of its 5 `aptest` scenarios miss the +-250 fpm / +-100 ft window; every other aircraft passes tuned, stock passes all; the stock Tutor is already marginal there, and the `apils` run already had 3 BAD rows before this round: jumbo, and two others, threshold-based); (2) top speed is not capped by Vne in the physics (stock aircraft already exceed Vne at low altitude with full power), only the overspeed warning and damage use the new Vne; (3) no fuel tank capacity upgrade (only burn rate) to keep the multi-tank jumbo model untouched; (4) the stat text "Range about" is only an estimate; (5) prices and effect sizes were never playtested by a human; (6) no refund or respec; (7) tuning is not shown on the AI traffic or in the chase view (it changes numbers only).

## Economy rebalance (2026-10-16)

What changed (all in `src/progress/catalog.js` and `src/modes/economy.js`, plus small UI text):
- **Starter fleet**: `START_AIRCRAFT = ['cessna172','caravan','trainer','citation','turboprop72','fighter']`, one per class (Light prop, Turboprop, Jet trainer, Business jet, Airliner, Fighter). `sanitizeSave` unions `START_AIRCRAFT` into every loaded/imported save, so existing saves and slots gain them with no migration code. Airports are 5-50 km apart (median about 16-27 km depending on the map), so "a short flight" is about 15 km.

Career and Emergency still charge 60% of it. A crash costs roughly one flight's pay.

## Ideas and open items
- Visual fidelity is the main gap versus "as realistic as possible": authored meshes and photographic textures are impossible in a code-only project, but more procedural work could help (gear well interiors, rivets and AO baked into body textures, real glass reflections, better fighter silhouettes, landing-light cones, visible cabin interiors).
- Performance on a real GPU is unmeasured (all browser tests are software GL). A hub with several parked airliners was not measured against the triangle budget; if the frame rate is poor, shorten the HIGH level switch distance in `aircraftView.js` (8 x length now) and check texture memory.
- Autopilot: no altitude alerter, VNAV, holds or SIDs/STARs; its approach hands back at 80 ft; the scripted widebody approach is about 1000 fpm hot at decision height; only tested headless plus a browser engage/disengage check.
- Time compression: mission clocks run on simulated time. Above 4x it needs the autopilot.
- The chart has no airspace, elevation contours or weather; it shows relief, roads, rails, towns, navaids, airports and the route.
- Free camera is not implemented. The cockpit camera was removed on purpose.
- The crash sequence and the chart were verified by screenshots under software rendering only; effect timings on a GPU will feel faster.
- Audio is tuned by reasoning, not by ear; ATC voices depend on the browser's speech synthesis.
- Model integrity is now checked automatically by `scripts/seethrough.mjs` (done 2026-10-16). Open follow-ups from it: the Skyhawk cabin-roof/wing-root hole, thin slivers under the airliner wing roots, the nozzle outer-shell rim gap, hollow missile tails, single-sided gear doors. Idea: make the script exit non-zero above a per-aircraft threshold and run it in the Pages workflow.
- Fence follow-ups (not requested): dust and a rattle sound on impact, a Career/VIP repair bill for fence strikes, AI aircraft colliding with fences, fence pieces and other airport props (windsocks, lights, signs) that can be knocked over the same way, a gate gap in the fence.
- Upgrade follow-ups (not requested): a tank-size track, a visible cue in the chase view for tuned aircraft (for example a badge in the debrief or a paint stripe), per-track price weights instead of one price curve per aircraft, upgrade refunds when selling, a pilot-wide "upgrade completionist" stat, damping the autopilot more for the Tutor.
- Missing but plausible next features: free camera, landing-light cones, ATC for the chart route, a pause-menu reposition option for Quick Flight.

## Decisions
- 2026-10-14 Plain JavaScript (ES modules), no TypeScript. Three.js WebGL2 only. Vite `base: './'`.
- 2026-10-14 Pushes go to the session branch `ccr-1a1faa50-o7g7vk`. The Pages workflow triggers on it plus main/master.
- 2026-10-14 World coordinates: +X east, +Y up, -Z north, metres. Heading 0 = north, 90 = east. Body frame: +X nose, +Y up, +Z right wing, origin at the CG. A runway end of heading h points along (sin h, -cos h); runway mesh yaw = pi - h.
- 2026-10-14 Key defaults: W = pitch down (stick forward), S = pitch up; everything remappable. Settings are a flat schema; the settings UI is generated from it.
- 2026-10-14 Physics: fixed 120 Hz with render interpolation. Stall speeds in aircraft data (KCAS at `mass.ref`) set CLmax per flap stage; `calibrateStall` solves the blend centre. Lift slope: Helmbold with Mach correction.
- 2026-10-14 Control law: `flightAssist` (off/light/full) plus fly-by-wire for fighters. Airborne starts are trimmed to equilibrium. Gear has a squat switch. Landing grades by sink rate; over `crashLanding` or an airframe strike ends the flight.
- 2026-10-15 Maps are fixed-seed 60 km squares (`MAP_HALF` = 30 km in `world/maps.js`; first 120 km, then 80 km, then 60 km after the user said the maps were a little too big). Airport counts are unchanged (13 / 12 / 11). Terrain is a quadtree of LOD tiles with skirts; normals use a fixed 48 m forward difference so LOD borders never show lighting seams. Physics ground height is the same analytic function (`Terrain.heightIn` for the mesh side).
- 2026-10-14 Biome look is one shader (`onBeforeCompile` on a standard material) driven by a zone texture (R farmland, G forest, B urban, A special) plus per-biome palettes: field patchwork and irrigation circles, street grid, desert strata, snow line. Custom shaders must `#include <common>` and the logdepth chunks, each `#include` on its own line.
- 2026-10-14 Airports: 1 hub, 2-3 regional, 4-5 airfields, 4 strips per map (11-13 airports). Sites are flat-searched, then the terrain is flattened to a pad. ILS on hub/regional main runways. Stands on aprons are in `layout.stands` and used by parked traffic.
- 2026-10-14 Weather presets (`SKY_PRESETS` visuals, `SKY_PHYSICS` forces): clear, scattered, overcast, rain, storm, fog, snow. Turbulence and wind shear act as angular kicks scaled by tas/mass. Cloud whiteout comes from visibility.
- 2026-10-14 Roster (14): 172, Caravan-class, L-39-class trainer, King Air-class, ATR-class, Citation-class, Gulfstream-class, E175-class, A320-class, 777-class, 747-class, F-16-class, F/A-18-class, Su-27-class. All names are generic ("Skyhawk 172", "Titan 400", ...); liveries are fictional.
- 2026-10-14 Heavy aircraft set `mass.ref` to a representative landing weight (stalls and gear are tuned there). `mass.fuelStart` puts typical total weight at or above ref. Airliner aileron derivatives are much larger than a light aircraft's to give a believable 10-15 deg/s roll despite huge inertia.
- 2026-10-14 Multi-tank fuel (`spec.tanks`, used by the jumbo): each tank has `capacity`, CG `arm` (fraction of MAC), burn `order` (ascending) and `feeds` (null = all engines, else engine indices). Engines draw from the lowest order first; loading fills the highest order first and shares equally within an order. CG = dry moment plus tank moments over total mass. Single-tank aircraft keep the linear empty-to-full CG.
- 2026-10-14 (updated 2026-10-15) Aircraft models are procedural, one file per aircraft or family: `cessna172.js`, `caravan.js`, `kingair.js`, `atr72.js`, `trainer.js`, `fighter.js`, `twinfighter.js` (Corsair and Warden), and the jet kit (`jetBuild.js`, `jetConfigs.js`, `jetFuselage.js`, `jetWing.js`, `jetEngine.js`, `jetGear.js`, `jetDetails.js`, `jetMaterials.js`, `jetTextures.js`) for the six jets (`citation.js`, `airliner.js` are thin wrappers). Shared kit: `kit.js` (lofted fuselages with optional end caps, airfoil wings, hinged surfaces, struts, `Parts` merge-per-material), `kitparts.js` (props, tyres, gear legs, lights, antennas, `ensurePlain`), `jetkit.js` (nozzles, missiles, canopy bows, seats), `skins.js` (env map, panel/rivet normal maps, painters, pro materials), `paintkit.js`, `bodypaint.js`, `lod.js`. Each aircraft has three LOD levels; the traffic baker (`traffic/fleet.js`) reuses them. Windows and panels are patches laid on the lofted skin (`bodyPatch`); cabin windows glow at night.
- 2026-10-14 AI traffic uses baked models (`traffic/fleet.js`): each LOD level is merged to one mesh per material, so a plane costs about 25 draw calls close and almost none far away; beyond 160 x its length it is not drawn. Parked aircraft are added when an airport is built; airborne traffic is scripted along straight legs between airports (8 aircraft per map).
- 2026-10-15 `models.html` + `src/dev/modelViewer.js` is a developer-only model viewer (not part of the game): `/models.html?id=jumbo&yaw=35&pitch=12&d=80` (yaw 0 looks at the tail, 90 from the right, 180 from the nose; params d, dist, tx/ty/tz, fov, lod, air=1 no ground, bg=<hex> background colour, night, sun, ab, rpm, flaps, aileron, elevator, rudder, speedbrake, gearext). `window.__info` reports draw calls and triangles.

- 2026-10-14 Modes: a mode is a set of `sys_*` settings (`game/modes.js`). Presets write all of them; changing one by hand sets the preset to Custom. `sys_realism` picks the flight assist at flight start (arcade full, standard light, full sim off). `damage` off disables overspeed, over-g, hard-landing and scrape destruction but not terrain impact. `fullWeather` off scales turbulence, shear and wetness down (`SimWorld.setRealism`).
- 2026-10-14 FlightControls owns throttle levers (master or per engine), automatic flaps (speed schedule with a latch so a level base leg does not flap) and automatic gear (up after takeoff, down on approach). The HUD levers and buttons call `setEngine`, `setMaster`, `setFlaps` and `perform(action)`.
- 2026-10-14 Systems (`flight/systems.js`): generators, APU, battery, hydraulics, pitot ice, control jam, fuel leak, fire timers. Failures come from `game/failures.js` (seeded random scheduler or `trigger`). Hydraulic loss: heavy controls, no gear or flap movement, weak brakes, no nosewheel steering; emergency gear extension still works. Telemetry `ias` is the displayed airspeed (affected by pitot ice); `iasTrue` is the real one and is what automation uses.
- 2026-10-14 Fuel handling: tanks have pumps; crossfeed lets any tank feed any engine; dump drains the fullest tanks down to landing weight (`spec.fuelDump`, kg/s). Piston mixture and propeller lever change power, thrust and fuel flow (`Engine.bestMixture`).
- 2026-10-14 ATC (`src/atc/`): `controller.js` is the player's state machine (phases parked, taxi, hold, lineup, rolling, departure, enroute, approach, final, rollout, taxi_in); requests come from a context menu of standard phrases, replies are built from the phraseology helpers with a short delay, and time follows model time (pausing stops it). The active runway is the best headwind end of the main runway (or the one you start on). Towered airports (hub, regional) give clearances; airfields and strips are uncontrolled (CTAF style). Approach vectors: heading to the initial approach fix, an intercept heading, "cleared approach, report established", then tower. Traffic advisories use scripted and AI aircraft. `aiTraffic.js` runs AI departures and arrivals with taxi paths from `geometry.js`, a runway occupancy check and go-arounds.
- 2026-10-14 Hub runway pairs: the main runway now sits 240 m left of the airport centre and the parallel 240 m right (it used to be centred on the terminal by mistake).
- 2026-10-14 HUD (`ui/flightHud.js`, `ui/hud/*`): draggable panels (`PanelManager`), shared tooltips, canvas panels reuse the cockpit painters. Panel hotkeys are on function keys because digits belong to the radio menu while it is open. `approachGuide.js` finds the runway you are lined up for and works without an ILS. `warnings.js` lists conditions; the HUD adds hold times, audio and the "red hides info" rule.

- 2026-10-14 Phase 5 structure: `src/progress/` (saves, catalog) and `src/modes/` (economy, tracker, missions, vip, emergency, freeflight, contract, runner). `ModeRunner` attaches a `FlightTracker` to a running session, forwards physics events and 10 Hz telemetry to the active mode, and `bank()` applies money and statistics to the active save then autosaves. Modes: `FreeFlightMode`, `ContractMode` (Career and VIP), `EmergencyMode`. UI lives in `ui/modeSelect, savesScreen, shopScreen, contractScreen, emergencyScreen, debrief, pilotBar, hud/missionPanel`.
- 2026-10-14 Quick Flight stays ungated and unsaved; gating (owned aircraft, upgrades) only applies in the save-based modes. Career, Emergency and VIP aircraft are loaned (no ownership needed). HUD gating is `PanelManager.lock(id, reason)`; the Terrain upgrade gates warnings via `evaluate(..., {gpws})`.
- 2026-10-14 Economy (credits, cr): start 10,000. Free Flight = paid km (min(track, 1.5 x straight + 15 km)) x rate + load revenue (pax x km x rate, or kg x km x rate) scaled by touchdown grade + landing fee x grade share + sights x (200 + 6 x rate), then the realism multiplier (arcade 1.0, custom 1.1, simulation 1.3). Contracts pay about twice the free-flight rate plus a tier bonus. Crash = no pay plus a repair bill (2 percent of the aircraft price, 250-25,000 cr; contracts 60 percent of that); insurance cuts it by 75 percent. Money never goes below zero. **SUPERSEDED on 2026-10-16 by the rebalance below (rates, landing fee, repair bill and starter fleet all changed; the structure and the realism multiplier are the same).**
- 2026-10-14 Landing grades (physics): Smooth under 150 ft/min, Good under 300, Firm under 500, Hard, Very hard. The tracker takes the worst touchdown within one landing (bounces count). A landing is complete when the aircraft is on the ground, under 5 kt for 2 s; a gear-up belly slide counts as a Hard landing. A flight leg starts at lift-off (or at the start if airborne).
- 2026-10-14 Missions are data in `missions.js`; airports are named by code (fixed-seed maps, validated by `modetest`). Time goal = about 1.35 x the estimated duration; hard deadline about 1.7 x; frugal goal = about 1.2 x the estimated burn (cruise burn table measured on the flight model); start fuel is the aircraft's usual load or 1.5 x the estimate plus a reserve (tight-fuel missions get 1.25 x plus 15 minutes).
- 2026-10-14 Emergency scenarios come from `generateScenario(seed)`: `Rng(seed)` picks difficulty (1-3), aircraft (mostly the tier's own pool), map, a suitable target airport (longest runway >= 1.05 x `minRunway`), failures (count 1/1-2/2-3, staggered 20-50 s) and the spawn: engine-out singles are placed within about 0.28-0.5 x glide range, others 12-38 km out; weather and time from the seed. Random failures are off in scripted flights (`options.scripted`). Failures are triggered by the mode with explicit engine/axis so the same seed repeats exactly.
- 2026-10-14 VIP comfort: loss per second from turbulence (|nz - 1| above 0.2 g), hard pulls (above 0.5 g, steeper), bank over 28 degrees, pitch rate over 5 deg/s, roll rate over 12 deg/s, descent faster than 2,200 fpm, climbs over 4,500 fpm, stall warning/stall, overspeed; recovery 0.35/s; touchdown knocks Firm 12, Hard 30, Very hard 60. Weather alone costs almost nothing (checked at 4 minutes in every sky). The cabin pack scales losses by 0.75.
- 2026-10-14 Saves: localStorage keys `flightsim:save:1..3` and `flightsim:activeSlot`, version 1, `sanitizeSave` repairs or rejects anything imported. Export files contain `{game:'flightsim', ...save}`.

- 2026-10-15 Phase 6: menu navigation is `ui/navigation.js` (spatial focus search over focusable elements inside the active screen, the crash card or the error overlay; polled on a 33 ms timer, not per frame, so it works when the 3D view is slow; while a menu owns the controller `Input.uiCapture` keeps buttons from reaching the aircraft). Audio is one shared `AudioContext` (`audio/audioBus.js`) with fx/voice/alert/ui buses driven by the volume settings; `EngineSound` rebuilds its voices per flight; everything is synthesized (oscillators, looped white/brown noise, filters). UI scale uses CSS `zoom` on `.screen` with `--ui-zoom` and `--vh = 100dvh / zoom` for heights; the HUD multiplies its own scale by the text size. Colour-blind mode swaps CSS variables (`--good`, `--warn`, `--danger`) and the canvas instrument `COLORS`.
- 2026-10-15 Decision: the cockpit view was removed completely (user: too complex). `CAMERA_MODES` = chase, cinematic, tower; the `sys_cockpitCam` setting is gone; the old cockpit code (`aircraft/cockpit/`) stays because its canvas painters drive the dashboard and HUD panels. A cockpit rebuild existed on an agent branch and was deliberately not merged.
- 2026-10-15 Decision: VIP comfort is gentler than before: loss from turbulence above 0.45 g (hard pulls above 0.9 g), bank over 40 degrees, pitch rate over 9 deg/s, roll rate over 20 deg/s, descents faster than 3,000 fpm, climbs over 4,500 fpm; stall 6/s, stall warning 1.5/s, overspeed 2/s; recovery 0.9/s; touchdown knocks Good 1, Firm 6, Hard 18, Very hard 40. (Replaces the older numbers in the Phase 5 entry above.)
- 2026-10-15 Decision: the navigation map is free and ungated in every mode; the Approach assist upgrade stays a shop item. The `gps` upgrade id no longer exists (`modetest` now buys `approach` for its purchase test).
- 2026-10-15 Decision (autopilot): inner pitch/roll loops run every physics step (rate damping needs it), guidance at 20 Hz; fighters use a bank-command law through the fly-by-wire (roll gain 0.012 per degree), light aircraft add a vertical-speed integrator (anti-windup under 400 fpm error); approaches lock onto the captured runway (`target`) so a second airport can never steal the localiser; the autothrottle moves the lever by a rate of 0.03 per knot of error minus acceleration damping. The pilot's throttle keys switch the autothrottle off.
- 2026-10-15 Decision (time compression): see Overhaul. Keys act per simulated second, so without the autopilot the cap is 4x.
- 2026-10-15 Decision (crash): breakup by cloning the visible LOD level into spatial buckets (no real lights; sprites for fire, smoke and flash); the crash menu is delayed 4.8 s real time.
- 2026-10-15 Decision (chart and waypoints): the chart is a screen (not a floating panel) and pauses by using the PAUSED state; waypoints are per flight (cleared on restart), at most 12, reached within 1 km; the autopilot's NAV follows them.
- 2026-10-15 Decision (UI theme): amber accent #ffb02e on warm charcoal, magenta for routes; avionics canvases keep cyan and green.
- 2026-10-15 Decision (model redo categories): light props = Skyhawk 172; turboprops = Trekker 208, Regal 200, Cirrus 72; jet trainer = Tutor T-39; airliners = the four airliners plus the two business jets; fighters = Falcon F-16, Corsair F/18, Warden S-27. Business jets carry no airline title.
- 2026-10-15 Decision (build stamp): `vite.config.js` defines `__APP_VERSION__` as "<package version> (<git short sha> <UTC time>)"; shown on the main menu and the About screen.
- 2026-10-15 Decision (landing grades and negative g): negative-g limit factor 3.2 (positive 1.45 unchanged).
- 2026-10-15 Menu backdrop is a 2D canvas (`ui/menuBackground.js`, 30 fps, one still frame with Reduce motion), moving only on the main menu. Adaptive resolution (`scene/adaptiveQuality.js`) scales the pixel ratio between 0.55 and 1 of its maximum in steps with cooldowns. `Terrain.update` skips the quadtree selection while nothing is pending and the camera moved under 20 m horizontally / 12 m vertically.
- 2026-10-15 Aircraft GPU resources are released when a flight ends (`aircraft/dispose.js`; textures marked `userData.shared` are kept). Checked over six start/quit cycles: texture and geometry counts stay flat.
- 2026-10-16 Decision (fences): fences are destructible scenery, not an obstacle that can crash the aircraft. The user explicitly asked that overshooting must not destroy the aircraft, so there is no damage, no crash and no score penalty; the only consequence is the momentum given to the debris (`FlightModel.applyImpulse`). Fence geometry moved from the merged airport buffers into two `InstancedMesh`es (bays and posts) so single pieces can be hidden by setting an instance matrix to zero scale; broken pieces are separate meshes with their own simple rigid-body physics in the airport frame; the collision hull is a coarse point/line model of the aircraft built from its `strike` and gear data. Pieces below 0.5 m/s contact speed never break (parked aircraft, pushback).
- 2026-10-16 Decision (approach guide): on-demand in every mode, including arcade; the state is reset (closed) at each flight start rather than remembered, because the saved panel state (`hudpanels`) previously carried an auto-opened panel into every later flight.
- 2026-10-16 Decision (model integrity): geometry that is wound the wrong way counts as a bug like a hole. Station lists for `loftBody` are sorted ascending by x inside `prepStations`, `revolve` is outward for either profile direction, `wingSurface` decides the skin orientation from one upper-surface triangle, loft end caps use the corrected winding. New model code should be run through `scripts/seethrough.mjs`.
- 2026-10-16 Decision (working practice): the headless checks (modetest, simtest, vite build) do not exercise rendering; for anything visual, drive a flight or the model viewer in Playwright and look at screenshots, and say plainly what was and was not checked on a real GPU.

## Known bugs / limits
- Upgrades (2026-10-16): see the last bullet of "Aircraft upgrades (2026-10-16)" (Tutor autopilot hunting when fully upgraded, no tank-size upgrade, balance never playtested).
- Not verified on a real GPU: all browser testing uses software rendering (about 5-15 fps). A hub view is about 700 draw calls and 0.5M triangles; the frame rate on target hardware needs the user's check.
- AI traffic: AI departures and arrivals run at airports (Phase 4) and scripted airliners fly legs between airports, but there is no collision with the player and no traffic avoidance by the player's autopilot.
- The headless test pilots land the fighters hard; a human should check approaches (F-16 at ~150 kt, AoA ~13 degrees; Corsair at ~140 kt, AoA ~8-10). The real autopilot's approach is within tolerance on 13 of 14 aircraft; the widebody arrives about 1000 fpm hot at decision height in the scripted test.
- Heavy aircraft need long runways (`minRunway`: 172 500 m up to Titan 3,300 m); only hubs have runways long enough for the jumbo.
- Headless software rendering runs the hub scene at about 1 fps (0.5M triangles), so all automated checks drive the simulation directly instead of relying on frame timing.
- ATC taxi guidance is text only: the player picks their own taxi route, the tower detects the hold-short point. AI aircraft do not use taxiways beyond the generated path and do not give way to the player on the ground.
- Cross runways have no taxiway connectors; AI and the hold-short point fall back to a straight line there.
- There is an autopilot (see Overhaul) but no FMS: routes are waypoint lists set on the chart.
- Free camera still not implemented. Tower view uses each airport's tower.
- Audio is synthesized and tuned by reasoning, not by ear on real speakers: levels may need a nudge (Settings > Audio). The ATC voice uses the browser's speech synthesis and so depends on the installed voices.
- Frame rate on a real GPU is still unmeasured; Auto quality is the safety net. Touch controls exist (see "Touch controls") but have only been tested with browser emulation, not on a real phone or iPad.
- Free Flight payloads are only for pay: passengers and cargo do not change the aircraft's weight.
- Emergency scenarios are not guaranteed survivable at the highest difficulty (it is the player's job); only engine-out singles are placed within glide range.
- Locking a panel (approach) closes it and the closed state is remembered for later Quick Flights. Since 2026-10-16 the approach guide is also closed at the start of every flight, in every mode.
- Fences (2026-10-16): the player's aircraft breaks them, AI aircraft ignore them; broken pieces are not saved and the fence is intact again after the airport streams out and in; the collision hull is points and lines; no sound or dust; untested on a real GPU with hundreds of loose pieces.
- Remaining see-through details (2026-10-16, not fixed): Skyhawk cabin-roof/wing-root patch, thin slivers under airliner wing roots, nozzle outer-shell rim, missile tails, single-sided gear doors (see the 2026-10-16 section and `scripts/seethrough.mjs`).
- The live site only deploys from `main`, `master` or `ccr-1a1faa50-o7g7vk` (the environment rejects other branches even if `pages.yml` lists them) (see `.github/workflows/pages.yml`); work on any other branch is invisible to the user until merged or pushed there. This round was pushed there on 2026-10-16 (run #40).
- The crash sequence and the chart were checked by screenshots in software rendering only; timings in real time on a GPU will feel faster (effects are capped at 50 ms steps).
- Models are procedural: not photoreal. Known approximations: trainer/F-16/Corsair/Warden silhouettes, flat glass, no rivets or baked AO, no gear well interiors, sprite lights. Texture memory about 30 MB per aircraft type.
- Pages serves the page with a short cache; right after a deploy a browser can run the previous build (check the build stamp on the main menu).
- Real-GPU frame rate, memory and the feel of the autopilot and time compression at real frame rates are unverified.

## How to run, test, deploy
- Install: `npm ci` (Node 22). Dev: `npm run dev`. Build: `npm run build`. Preview: `npm run preview`.
- Phase 6 checks are Playwright scripts kept out of the repo (menu navigation with a fake gamepad, audio level via an analyser tap `__flightsim.audio.level()`, all-aircraft console sweep, memory/leak cycle, CPU profile of update/render). `window.__flightsim` also exposes `audio` and `engineSound`.
- Phase 5: `node scripts/modetest.mjs` (catalogue, saves, economy, all 37 missions and 10 VIP contracts resolve, 300 emergency seeds repeat, scripted landings through Free Flight, Career, Emergency, VIP and a full takeoff-to-landing leg). `DEBUG=1` prints a trace.
- Physics: `node scripts/simtest.mjs [id]` (takeoff, cruise per assist level, stalls, landing, hard landing), `node scripts/kbtest.mjs [id]`, `node scripts/authority.mjs [id]`.
- Browser tests: Playwright + system Chromium with `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`; `window.__flightsim` exposes state/session/settings. `startFlight({aircraftId, mapId, airportCode, endId, startMode, hour, sky})` runs a flight.
- Autopilot: `node scripts/aptest.mjs [id]` (altitude, heading and V/S scenarios, all 14 must pass) and `node scripts/apils.mjs [id]` (ILS from 16 km, `V=1` prints a trace).
- See-through check (after any model change): start the dev server, then `node scripts/seethrough.mjs <id|all> [distance] [outDir]` (about 1 minute per aircraft with software GL; overlays go to `/tmp/seethrough`). Yellow = hole, red = inside-out; compare against the numbers in the 2026-10-16 section. Then also look at the in-game chase view from behind (the user's reports came from there). The old method (magenta background, look for holes by eye) misses wrongly wound faces.
- Fence test recipe: see the 2026-10-16 section (reset the aircraft 80 m before `userData.fence.edges[1]` of the first built airport, set velocity, step `session.update(1/120)` and `flightScene.airports.update(camPos, wind, 1/120)`).
- Playwright helpers used this session (not in the repo): start a flight and screenshot (wait for `__flightsim.state.current === 'flying'`, then 3-6 s), crash test (`session.model.crashWith('x')`), chart test (press M, click the canvas, Esc), model viewer shots at several yaw/pitch/d values, and a montage of five views per aircraft with ImageMagick.
- Deploy: push to `main`, `master`, or `ccr-1a1faa50-o7g7vk` (the only branches that can deploy: `ccr-68ab36c0-on6hut` is also listed in `pages.yml` but the github-pages environment rejects its deploy job, so always fast-forward `ccr-1a1faa50-o7g7vk`; other session branches such as `claude/laughing-johnson-p3xxpp` are not deployed); the workflow builds and publishes to Pages (about a minute; runs are numbered in the Actions list). Check with the GitHub MCP `actions_list`. Pages caches for up to 10 minutes.
